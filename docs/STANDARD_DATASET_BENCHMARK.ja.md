# LFW と WIDER FACE によるローカル標準データセット性能テスト

[English](STANDARD_DATASET_BENCHMARK.md) | [简体中文](STANDARD_DATASET_BENCHMARK.zh-CN.md) | [日本語](STANDARD_DATASET_BENCHMARK.ja.md)

本書は速度、資源使用量、実装間の一致性を記録する。後続の評価では **LFW 全 6,000 ペアの 10 fold 正解率、WIDER 検証画像全 3,226 枚の検出 AP、声優ホールドアウト全 1,051 枚の再評価**を完了した。[完全版の精度報告](STANDARD_DATASET_ACCURACY.ja.md)を参照。

2026-10-28、Apple M4 Pro / 24 GiB の本機で、**公開データセット画像 756 枚、独立サービスプロセス 6 個、計測 HTTP リクエスト 9,072 件**を使い、Python と C++/Go を比較した。3 回の出力一致検査と独立した統計監査がすべて通過した。

**完全な認識処理の平均時間の削減は約 1.8%–2.7%、ピーク RSS 中央値の削減は約 3.8% だった。** 検出のみでは約 7.9%–14.7% と大きな削減が得られた。本機の完全認識では依然としてモデル計算が主要な処理時間を占め、言語移行自体の効果は限定的だった。この比較は Mac ARM、FTZ/DAZ 無効での結果である。N150 の FTZ/DAZ の効果は [N150 実測報告](N150_BENCHMARK.ja.md)に分けて記録しており、両者の結果を混同しない。

## 入力と出典

| データセット | 元の範囲 | 今回固定した抽出 | 画像の特徴 |
| --- | --- | --- | --- |
| LFW 原版、non-funneled | 13,233 枚、5,749 人 | 512 人から各 1 枚、計 512 枚 | 元の 250 × 250 JPEG。通常は主要な顔が 1 つあり、背景の顔を含む場合もある |
| WIDER FACE validation | 3,226 枚、61 シーンカテゴリ | 各カテゴリ 4 枚、計 244 枚 | 複数人物、小顔、遮蔽など。今回の画像はすべて幅 1,024、高さ 351–2,014 |

LFW は[固定リビジョンのミラー](https://huggingface.co/datasets/DerrickUnleashed/LFW/tree/f7571fa9dd5a5c31ab781de5227c6f1b6171c0c5)からダウンロードした。アーカイブの SHA-256 は [scikit-learn のデータ定義](https://github.com/scikit-learn/scikit-learn/blob/main/sklearn/datasets/_lfw.py)と一致する。WIDER FACE は [CUHK-CSE の固定リビジョンミラー](https://huggingface.co/datasets/CUHK-CSE/wider_face/tree/833d07e7bf3860f294242312fe95eed0561eeb17/data)を使用した。データの範囲と用途は [WIDER FACE プロジェクトページ](https://mmlab.ie.cuhk.edu.hk/projects/WIDERFace/index.html)を参照。

| ファイル | SHA-256 |
| --- | --- |
| `lfw.tgz` | `055f7d9c632d7370e6fb4afc7468d40f970c34a80d4c6f50ffec63f5a8d536c0` |
| `WIDER_val.zip` | `f9efbd09f28c5d2d884be8c0eaef3967158c866a593fc36ab0413e4b2a58a17a` |
| `wider_face_split.zip` | `c7561e4f5e7a118c249e0a5c5c902b0de90bbf120d7da9fa28d99041f68a8a5c` |

抽出は推論前に固定し、シード文字列 `20261028-standard-benchmark-v1` を使い、`SHA256(seed + ':' + 相対パスまたは人物名)` で並べた。LFW は先に 512 人を選び、その後各 1 枚を選択した。WIDER は各カテゴリ内で 4 枚を選択した。モデル出力に基づく選別、再エンコード、クロップ、入力解像度変更は行わず、既存アプリの検出時リサイズ、品質閾値、認識処理を適用した。

選択画像のみを展開し、合計約 33.9 MiB だった。完全なダウンロードアーカイブと結果を含め、今回のディレクトリは約 578 MiB となった。データと画像ごとの応答は Git 無視対象の実験ディレクトリに保存し、リポジトリやモデル Release に含めない。

## 計測方法

環境は macOS 26.6.2 ARM64、Apple M4 Pro（論理 CPU 14 個）、メモリ 24 GiB。Python 3.13.15、NumPy 2.5.2、ONNX Runtime 1.29.0、OpenCV Python 5.0.0.93、Pillow 12.3.0、FastAPI 0.154.0、Uvicorn 0.54.0 を使用した。ネイティブ版は Go 1.26.2、C++、OpenCV 5.0.0、ONNX Runtime 1.29.0 による macOS ARM ビルドだった。

両実装は同じ FP32 モデルと分類ヘッドを使用し、`configs/n150.yaml` のスレッド設定を適用した。各バックボーン 1 スレッド、2 バックボーン並列、検出器 2 スレッド、スピン無効、CPU arena 有効である。既定の Top-5 と閾値 0.95 も同じ。ネイティブ JSON では `flush_denormals` を有効にしていない。現行 FTZ/DAZ 実装の対応は Linux x86_64 に限られる。

各サービスプロセスで、両データセットについて次の 2 経路を計測した。

- `/v1/detect` はアップロード、デコード、検出、応答を含む。
- `/v1/recognize` はアップロード、デコード、検出、品質検査、条件を満たす顔の位置合わせと 2 バックボーン分類、応答を含む。

各フェーズで先に非計測のウォームアップを 10 回行い、そのデータセットの選択画像すべてを各 1 回リクエストした。各実装を新規プロセスで 3 回実行し、順番は `Python → native → native → Python → Python → native` とした。後のラウンドではデータセットと API フェーズの順番も変えた。同時に動かす被測定サービスは 1 つだけとし、単一クライアントで逐次リクエストした。並行負荷試験やバッチ推論は行っていない。合計 **計測 9,072 件、ウォームアップ 240 件**だった。

画像のバイト列はクライアントメモリに事前ロードした。HTTP 時間はローカルループバック経由のアップロードから応答完了までを測り、クライアントと接続のオーバーヘッドを含む。純粋なモデル時間や公衆網のアップロード体験を示す値にはならない。スループットは逐次リクエストフェーズ全体の件数を所要時間で割った値で、ループと応答処理を含む。並行時の限界スループットを示すものではない。

CPU 時間は macOS `proc_pid_rusage(RUSAGE_INFO_V2)` からサービスプロセスの user + system 時間を取得し、`mach_timebase_info` の `125/3` により Mach ticks をナノ秒に変換した。計測前に自身の `process_time_ns` で較正確認を行った。CPU ミリ秒／リクエストはサービスの全スレッドを含み、クライアントを含まず、マシン全体の消費電力量を示さない。ピーク RSS は各サービス終了後の `wait4` で取得し、起動、全ウォームアップ、両データセット、両 API を含む。データセットごとのフェーズピークには分割していない。

表は **3 プロセスそれぞれの指標の中央値**を示す。P95 は各プロセスの nearest-rank P95 を求めてから中央値を取った値で、3 回分のリクエストを統合した全体 P95 ではない。日常のバックグラウンドアプリは動作を続けた。CPU 周波数の固定、システムキャッシュ消去、温度制御は行っておらず、数パーセントの差は今回のワークロードの範囲で解釈する。

## 完全認識の結果

| データセット | 実装 | 平均 HTTP | P50 | P95 | 逐次スループット | CPU／リクエスト |
| --- | --- | ---: | ---: | ---: | ---: | ---: |
| LFW 512 枚 | Python | 59.91 ms | 54.46 ms | 93.99 ms | 16.69 枚/s | 100.98 ms |
| LFW 512 枚 | C++/Go | **58.82 ms** | 53.13 ms | 92.11 ms | 17.00 枚/s | 100.57 ms |
| WIDER 244 枚 | Python | 77.39 ms | 58.87 ms | 212.00 ms | 12.92 枚/s | 130.35 ms |
| WIDER 244 枚 | C++/Go | **75.33 ms** | 55.87 ms | 210.70 ms | 13.27 枚/s | 128.87 ms |

平均 HTTP 時間は LFW で **1.83%**、WIDER で **2.67%** 減少した。CPU 時間の減少はそれぞれ約 **0.41%** と **1.13%** で、小さな効果にとどまった。両実装は引き続き同じ 2 バックボーン計算を実行する。

各ラウンドの完全認識の処理量は Python と C++/Go で完全に同じだった。

| データセット | 検出顔数 | 分類に進んだ顔数 | 品質で除外 | 顔なし画像 | 1 画像の最大検出顔数 |
| --- | ---: | ---: | ---: | ---: | ---: |
| LFW | 645 | 579 | 66 | 1 | 9 |
| WIDER | 1,219 | 363 | 856 | 14 | 105 |

したがって WIDER の 75.33 ms は品質フィルタを含むアプリ全体の処理であり、各画像の全注釈顔が 2 バックボーンを実行したという意味にはならない。抽出した WIDER の注釈顔数は 2,892、有効とされた顔は 2,872。今回は公式規則で検出枠を照合していないため、これらを単純に割って再現率を求めることはできない。

| --- | --- | ---: | ---: | ---: | ---: |
| LFW | Python | 15.95 ms | 16.57 ms | 62.64 枚/s | 21.28 ms |
| LFW | C++/Go | **14.69 ms** | 15.32 ms | 68.02 枚/s | 20.03 ms |

平均 HTTP 時間はそれぞれ **7.90%**、**14.69%** 減少した。画像デコード、データ処理、HTTP 経路の違いを含むため、差のすべてを言語自体に帰属させない。

## メモリと起動

| 実装 | ピーク RSS 中央値 | 3 プロセスのピーク RSS | 起動から準備完了までの中央値 |
| --- | ---: | --- | ---: |
| Python | 1,012.89 MiB | 1,012.89 / 1,043.66 / 1,002.08 MiB | 796.20 ms |
| C++/Go | **974.42 MiB** | 891.22 / 989.34 / 974.42 MiB | 466.89 ms |

ピーク RSS 中央値は **38.47 MiB／3.80%** 減少したが、プロセス間の変動は大きい。ネイティブ版の起動時間は 1,344.69 / 395.80 / 466.89 ms、Python は 934.42 / 796.20 / 633.85 ms だった。コールドキャッシュ条件を統一していないため、中央値だけでコールドスタートが常に速いとはいえない。

## 出力一致性と精度の限界

3 ラウンド、2 データセット、2 API の **12 組の比較がすべて通過**した。各実装のプロセス間出力も、処理時間フィールドを除いて完全に再現した。完全認識では次を確認した。

- 顔数、検出枠、検出スコアが一致し、候補人物の順序、品質判定、閾値 0.95 の受理判定も一致した。
- 分類確率の最大絶対差は **`3.5762786865234375e-7`**、品質スコアの最大差は約 `2.22e-16` だった。
- 数値はビット単位では一致しない。既存検証ツールの許容差を維持し、枠／ランドマークは 0.01 ピクセル、スコアは `5e-5` とした。
- 各ラウンドで、実際に分類した 942 顔はすべて確率不足により人手確認対象となり、別の 922 顔は品質検査で除外された。今回の入力では自動受理が発生しなかったが、未知人物の誤識別率がゼロという結論にはならない。

本試験は**標準データセットの部分集合におけるシステム性能と実装一致性のテスト**であり、50 クラス分類ヘッドは再訓練していない。LFW の人名をそのまま現行ヘッドのラベルには使えない。この試験では LFW の 6,000 ペア・10 fold 検証プロトコルや WIDER 公式 Easy / Medium / Hard AP の計算を行っていない。既存の **98.48%** は従来の声優ホールドアウト集合の成績であり、今回の標準データセット精度ではない。
