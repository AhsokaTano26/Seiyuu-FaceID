# Intel N150 実機検証とネイティブランタイム、精度、3 構成の性能比較

[English](N150_BENCHMARK.md) | [简体中文](N150_BENCHMARK.zh-CN.md) | [日本語](N150_BENCHMARK.ja.md)

本書は 2026-10-27 に Linux / Intel N150 / 8 GB のマシンで行った検証を記録する。Linux ネイティブビルド、動的ライブラリのロード、実モデルの API 検査、歴史的ホールドアウト全入力での Python/C++ 一致性検証を完了した。**3 構成の HTTP ベースラインと後続の独立した FTZ 候補実験は完了し、独立監査を通過した。** 元のベースラインでは言語変更自体による確実な高速化は見られなかった。非正規化数処理の負荷を特定した後、FTZ 候補の平均 HTTP 時間は **680.785 ms** となり、歴史的ホールドアウトの正解率は **1,035 / 1,051 = 98.48%** を維持した。

候補と先のベースラインは同じ入力を使い、別の段階で実行した。同時期に交互実行する A/B 比較は行っていない。第 6 節に元の 3 構成ベースラインを保持し、第 8 節に診断、実装、全量回帰、候補 HTTP 結果を分けて記録する。**検証済み実装は 2026-10-28 に製品ソースへ統合し、N150 で有効化した。配備受入検査は第 9 節を参照。**

元の FP32 モデル、分類ヘッド、受理閾値を維持し、スレッド設定変更と C++/Go ランタイム移行をそれぞれ調べた。アルゴリズムと実装原理は[技術詳解](TECHNICAL_ARCHITECTURE.ja.md)、ビルド手順は [C++ + Go 試験版ガイド](NATIVE_CPP_GO.ja.md)を参照。

## 1. 検証済み環境

| 項目 | 今回の環境 |
| --- | --- |
| プロセッサ | Intel N150、利用可能な論理 CPU 4 個 |
| メモリ | 公称 8 GB、システムから約 7.535 GiB を認識 |
| システム | Linux x86_64、カーネル `6.8.0-142-generic`、glibc 2.39 |
| CPU governor の記録 | 4 CPU とも `powersave` |
| Python 参照環境 | Python 3.12.3、NumPy 2.5.2、ONNX Runtime 1.29.0 |
| Python 画像依存 | OpenCV 5.0.0、配布パッケージ `opencv-python 5.0.0.93`、Pillow 12.3.0 |
| ネイティブコア依存 | ONNX Runtime 1.29.0、OpenCV 5.0.0 |
| ストレージ配置 | 主 SSD にビルド、モデル、テスト入力を準備。機械式データディスクには移していない |

`powersave` は採取時の周波数制御ポリシーであり、CPU が一定の低周波数に固定されたことを意味しない。ハードウェア記録には周波数と温度のスナップショットも保存した。単一記録で試験全体の周波数や温度が一定だったと証明することや、継続的なクロック低下の有無を判断することはできない。

正式計測中のあるプロセス記録では、被測定 Python プロセスの nice 値は 0、CPU affinity は `0–3` だった。所属 cgroup と上位 cgroup に CPU 時間のハードクォータはなく、取得した quota throttling カウントは 0 だった。この時点での単一コア固定と cgroup クォータ制限は除外できるが、温度、電力、試験全体のスケジューリング監視の代わりにはならない。

既存の業務コンテナは動作を継続し、試験前にバックグラウンド負荷を記録した。その時点の既存 FaceID サービスは約 970 MiB を使い、CPU 使用率は低かった。これは背景条件の記録であり、被測定サービスの性能値や実験全体で干渉がなかったことを示すものではない。試験のために既存サービスを停止したり、コンテナを再作成したり、データディスクのマウントを変更したりしていない。

## 2. Linux ビルドと起動検査

対象機でネイティブビルドを完了し、次の結果を確認した。

- アプリの共有ライブラリ依存を解決でき、サービス実行ファイルのヘルプコマンドが正常終了した。
- ELF の相対ロードパスは `$ORIGIN/../lib` で、アプリの隣にある同梱共有ライブラリを探索する。
- C++ CTest は **2 件通過**した。
- Go の通常テスト、ネイティブコア有効のビルドテスト、実モデル HTTP 統合テストが通過した。
- Python のモデル出力・ネイティブ検証関連テストは **20 件通過**した。

ここに記録したのは今回 N150 で実行した範囲である。以前 Mac で実行した Python 全 206 テストの記録は過去のものであり、N150 で全 206 件を再実行したという意味にはならない。

ネイティブサービスは実行ファイル、共有ライブラリ、モデル、設定で構成され、静的な単一ファイルプログラムではない。上記ロード検査は本機の現在のシステム環境で動作することを示すが、任意の Linux ディストリビューションやシステムライブラリ版への互換性を証明するものではない。

数値検証では Python ドライバが参照実装と C API ワーカーを別々に起動した。ドライバの Python 依存は入力準備と結果比較に使うもので、Go HTTP サービスの実行時に Python が必要という意味ではない。C API の数値検証も Go のアップロード、認証、レート制限、API 統合テストを代替しない。両検査は別々に記録した。

## 3. 入力、モデル、設定の固定方法

実行前に入力リストを作り、ハッシュを計算した。

- **歴史的ホールドアウト顔クロップ 1,051 枚**で、全特徴、分類確率、個人識別結果を比較した。
- **ホールドアウト由来の原画像 12 枚**から **14 顔**を検出し、デコード、検出、位置合わせ、分類の全経路を比較した。HTTP 性能実験の固定入力にも使用した。

12 原画像の検出結果は単一顔画像 11 枚と 3 顔画像 1 枚だった。条件を満たす各顔で両バックボーンを実行するため、後述の時間と P95 は入力顔数にも影響される。この混合入力の P95 を単一顔写真のランダムな遅延末尾として解釈することはできない。

両実装は同じファイルリスト、FP32 重み、元の分類ヘッド、順序付きクラス名を使った。異なるビルドや入力を混在させないよう、設定、出力 JSON、コアライブラリ、サービスバイナリ、テストスクリプトのハッシュも固定した。Python YAML とネイティブ JSON は元々ハッシュが異なる。比較対象は出力後の設定の意味的一致であり、形式の異なるファイルのバイト一致は求めていない。

全構成で次の設定を維持した。

| 設定 | 値 |
| --- | --- |
| 検出前処理の長辺上限 | 1920 ピクセル |
| SCRFD 入力 | 640 × 640 |
| 検出閾値 / NMS 閾値 | 0.50 / 0.40 |
| 顔の最小短辺 / 最低鮮明度 | 48 ピクセル / Laplacian 分散 20.0 |
| 既定候補数 / 受理閾値 | 5 / 0.95 |
| 検出器 intra-op スレッド | 2 |
| inter-op スレッド / CPU arena | 1 / 有効 |

今回の 12 原画像は歴史的ホールドアウト由来である。**以前の Mac HTTP 実験の 12 原画像は訓練由来だった。** Mac と N150 の平均時間を直接割り、同一ワークロードでのハードウェア速度比を求めることはできない。

## 4. 完了した精度と一致性の結果

全量数値比較は `python_n150` と `native_n150` を対象とした。いずれも各バックボーンの intra-op は 1 スレッド、バックボーン並列、スピン無効、検出器は 2 スレッドとした。同一プロセス内の動的ライブラリ干渉を避けるため、Python と C++ は別ワーカーで動作した。

正しさの計算の一部はビルドや別の正しさ検証ワーカーと重なったため、その時間は性能結論に使わない。正式な HTTP 計測は全ビルド・正しさ検証ワーカーの終了後に開始した。

### 4.1 歴史的ホールドアウトの全クロップ

| 指標 | Python N150 設定 | C++ N150 設定 |
| --- | ---: | ---: |
| クロップ数 | 1,051 | 1,051 |
| テスト真値のあるクラス数 | 49 | 49 |
| Top-1 正解数 | 1,035 | 1,035 |
| Top-1 誤り数 | 16 | 16 |
| Top-1 正解率 | 98.48% | 98.48% |
| Top-5 正解率 | 99.14% | 99.14% |
| 対象クラス Macro-F1 | 99.10% | 99.10% |
| 閾値 0.95 での受理数 | 1,011 | 1,011 |
| うち誤受理数 | 4 | 4 |
| 要確認数 | 40 | 40 |

全 1,051 クロップで第 1 候補、順序付き Top-5、閾値 0.95 の受理判定、クラス順が一致した。参照実装に対し C++ は**新規誤り 0 件、修正誤り 0 件**だった。

| 数値比較 | 実測の最大絶対差 |
| --- | ---: |
| 1024 次元特徴 | `2.2351741790771484e-8` |
| 分類確率 | `4.76837158203125e-7` |

数値許容差検査は通過したが、特徴と確率はビット単位で同一ではない。絶対許容差は特徴 `2e-5`、確率 `5e-6`、相対許容差は 0 とした。候補順と受理判定は別途確認し、浮動小数点配列が近いだけで判定不変とは結論しない。

受理・要確認数は、位置合わせ済み既知人物クロップの分類結果である。原画像の未検出や品質除外を含まず、未知人物の誤受理率も表さない。49 はこのホールドアウトで真値のあるクラス数で、モデルには引き続き 50 人を内蔵する。

### 4.2 原画像と直接デコード経路

12 原画像、14 検出顔について、事前デコード BGR 経路と圧縮ファイルのネイティブ直接デコード経路を比較した。

- 顔数、検出枠、検出スコア、品質スコアが一致した。
- 全 14 顔の候補順と受理／要確認判定が一致した。
- 両経路の分類確率の最大絶対差はともに `2.384185791015625e-7` だった。
- デコード後の画像サイズが一致した。Python ワーカー間、ワーカーと入力準備段階のデコード結果も一致した。

実際の原画像処理を含むが画像数は 12 枚であり、すべての JPEG エンコード、EXIF 方向、極端なサイズ、顔の重なりを網羅するものではない。

### 4.3 結論の適用範囲

**今回の N150 入力では、C++/Go 構成の C++ 推論コアによる個人識別・受理判定の退行はなかった。** Linux ネイティブサービスもロードでき、実施した HTTP 統合検査を通過した。

これは新しい独立した汎化性能の証明にはならない。歴史的ホールドアウトは以前のモデル選択に使用され、画像間に出典の相関が残る可能性がある。両実装が同じ誤った人物を返した場合にも一致性は成立するが、識別の正しさは成立しない。未知人物、ギャラリー外人物、任意入力の拒否能力は別のデータと指標を必要とする。

全 1,051 クロップの比較が対象とするのは N150 設定の Python と C++ である。後述の `python_original` は別のスレッド設定を復元する。HTTP 実験は 12 原画像で 3 構成の一致を確認したが、旧スレッド構成でも全 1,051 クロップを再検証したという意味にはならない。

## 5. 3 構成 HTTP 性能実験のプロトコル

### 5.1 各構成が調べる事項

| 構成名 | 実装と環境 | バックボーン intra-op | バックボーン実行 | スピン |
| --- | --- | ---: | --- | --- |
| `python_original` | 現在の Python ソースと固定環境で、本番の旧スレッド設定を再現 | 各 2 スレッド | 逐次 | 有効 |
| `python_n150` | 同じ Python ソース、インタプリタ、依存で N150 設定を使用 | 各 1 スレッド | 並列 | 無効 |
| `native_n150` | C++ コアと Go HTTP、対応する N150 設定 | 各 1 スレッド | 並列 | 無効 |

`python_original` の original は**旧実行パラメータの再現だけを指す**。現在の Python 3.12.3 環境とソースを使い、既存の本番 Python 3.13 サービスを直接計測したり、本番ポートへベンチマークリクエストを送ったりしていない。Python 2 構成のインタプリタと依存を同じにし、スレッド設定と環境版変更の効果を分離した。

`python_original` と `python_n150` の比較は主に設定変更を、`python_n150` と `native_n150` の比較は同じモデル・実行設定でのランタイム全体の移行を調べる。後者にも画像デコード、オブジェクト割当、HTTP 実装の差が含まれ、すべてを C++ 言語自体の効果とはいえない。

### 5.2 リクエストと実行順

正式プロトコルは最初の計測プロセス開始前に固定した。各構成で独立した新規サービスプロセスを 3 回起動した。各プロセスは同じ 12 原画像で全体 1 周のウォームアップと 4 周の計測を行い、**ウォームアップ 12 件、計測 48 件**とした。

3 反復の起動順は次のとおり。

1. `python_original` → `python_n150` → `native_n150`。
2. `python_n150` → `native_n150` → `python_original`。
3. `native_n150` → `python_original` → `python_n150`。

計 9 被測定プロセス、432 計測リクエストとなる。同時に動かす被測定サービスは 1 つだけとし、正式計測にビルドや正しさ検証を重ねなかった。本番と他のバックグラウンドサービスは継続稼働し、負荷を記録した。順序の交代で固定順の影響を減らすが、温度、キャッシュ、バックグラウンド処理の変動をすべて除去できるわけではない。

各計測リクエストでも 3 設定間の出力一致を確認した。性能集計では完了状態、プロセス数、リクエスト数、出力比較を合わせて確認する必要がある。部分的な時間出力だけで実験完了とは判断しない。

### 5.3 各指標の計算法

| 指標 | 定義と範囲 |
| --- | --- |
| HTTP wall time | ローカルクライアントのアップロードから JSON 応答解析まで。ローカル転送と応答処理を含む |
| サーバー処理時間 | サービス記録の範囲で、読取、デコード、推論を含む。先行する multipart 解析と待ち行列は含めない |
| 計測区間 CPU 時間 | 48 計測リクエスト前後の `/proc/<pid>/stat` の `utime + stime` 増分をシステムクロック周波数で割った値 |
| 生涯 CPU 時間 | `wait4` が返すプロセス累積 CPU。ロード、ウォームアップ、終了を含み、計測区間 CPU とは別保存 |
| ピーク RSS | モデルロード、ウォームアップ、大画像処理を含むプロセス全稼働期間のピーク。Linux KiB を MiB に変換 |
| 起動時間 | 新規プロセス起動から準備完了まで。新規プロセスはファイルシステムのコールドキャッシュを意味しない |

平均、P50、P95 は各プロセスの 48 リクエスト内で求め、その後同じ構成の 3 プロセス指標の中央値を取った。分位数は nearest-rank を使い、48 値を昇順に並べた第 24 値を P50、第 46 値を P95 とした。**3 プロセスの 144 リクエストを統合して P95 を再計算していない。**

CPU 時間は関連する全スレッドの累積プロセッサ時間で、ユーザーの待ち時間や電力量とは異なる。マシン全体の電力サンプリングがないため、CPU 時間比を直接節電率に置き換えない。ピーク RSS にもホスト全体と他サービスのメモリは含まれず、マシン全体の使用量を主張できない。

## 6. 完了した 3 構成のベースライン結果

### 6.1 完了状態と集計

最終報告は `complete` とされ、各構成が 3 プロセス、各プロセスが 48 計測リクエストを完了し、合計 **432 計測リクエスト**となった。各反復で 3 構成の全ペアを比較し、計 9 組で全リクエストの顔数、候補順、判定が一致した。

独立監査では完全性、件数、集計演算、相対変化を再確認して通過した。非公開の各サンプル出力は再読込せず、性能向上を監査合格条件にもしていない。性能の結論は以下の実測値に基づく。

表の各セルは該当指標の **3 プロセスの中央値**である。時間単位は秒、CPU 時間は累積プロセッサ時間である。

| 指標 | `python_original` | `python_n150` | `native_n150` |
| --- | ---: | ---: | ---: |
| 平均 HTTP 時間、s/リクエスト | 8.277 | 11.415 | 11.401 |
| HTTP P50、s/リクエスト | 7.119 | 9.797 | 9.780 |
| HTTP P95、s/リクエスト | 21.000 | 29.207 | 29.165 |
| 平均サーバー処理時間、s/リクエスト | 8.252 | 11.393 | 11.380 |
| 計測区間 CPU 時間、CPU s/リクエスト | 20.937 | 13.731 | 13.710 |
| 計測区間の平均使用コア数 | 2.529 | 1.203 | 1.203 |
| プロセスのピーク RSS、MiB | 751.27 | 758.95 | 906.97 |

これは 3 顔画像 1 枚を含む固定 12 画像の混合ワークロードである。P95 は 3 顔画像の計算量に影響され、固定単一顔入力で偶然 20 秒超のランダム遅延が発生したという読み方はできない。既存本番ポートの直接測定でもない。

### 6.2 設定変更による CPU 時間削減と待ち時間増加

`python_original` に対し `python_n150` は次のように変化した。

- 計測区間 CPU 時間は **20.937 から 13.731 CPU s/リクエストへ 34.4% 減少**した。
- 平均 HTTP 時間は **8.277 から 11.415 s/リクエストへ 37.9% 増加**し、P95 は約 39.1% 増加した。
- ピーク RSS は 751.27 から 758.95 MiB へ約 1.0% 増加した。

今回の入力で N150 プリセットは CPU 作業量と遅延のトレードオフを示し、両方の同時削減は達成しなかった。旧スレッド構成の平均使用量は約 2.53 コア、N150 設定は約 1.20 コアだった。累積 CPU 時間の減少は待ち時間短縮を意味せず、マシン全体の節電率にも直接変換できない。

### 6.3 言語移行による高速化や省メモリは実証されなかった

同設定の `python_n150` に対し `native_n150` の平均 HTTP 時間は約 **0.12%**、P95 は約 0.14%、計測区間 CPU 時間は約 0.15% 低いだけだった。3 プロセスの平均時間の最大・最小差は Python 中央値の約 0.24%、ネイティブ中央値の約 0.65% だった。構成間の 0.12% 差は各反復の変動幅より小さく、確実な高速化とはいえない。

ネイティブのピーク RSS は **906.97 MiB** で、同設定 Python の **758.95 MiB** より約 **148.02 MiB、19.5%** 高かった。以前の Mac 結果をもって今回の N150 ネイティブ実装の省メモリを主張することはできない。

旧スレッド Python 構成に対しても、ネイティブ平均 HTTP 時間は約 37.7%、ピーク RSS は約 20.7% 高く、計測区間 CPU 時間は約 34.5% 低かった。これらには実行設定と実装の両方の差が含まれ、すべてを Go や C++ に帰属させることはできない。結果は精度・判定回帰の通過を支持するが、参照実装に対する全面的優位性を示すものではない。

### 6.4 環境と結論の限界

## 8. FTZ / DAZ の独立した追試

この節は 3 構成ベースライン完了後の独立実験である。3 クロップの数値・kernel 診断、独立候補コアのビルド、少数 C API 検査、全 1,051 クロップと 12 原画像の回帰、および **3 新規プロセスの HTTP 計測をすべて完了**した。最終報告は独立監査を通過した。この結果で第 6 節を置き換えることはなく、この時点で実験設定を本番適用したという意味でもない。

### 8.1 非正規化数を調べる理由

FP32 はゼロに非常に近い非ゼロ値を表現できる。絶対値が最小正規数 `2^-126` より小さい非ゼロ値を非正規化数（subnormal、denormal とも呼ぶ）という。段階的アンダーフローを支えるが、特定のプロセッサや命令経路では大きな計算負荷を生む場合がある。

元の ONNX の FP32 初期化テンソルを読取専用で数え、以下の結果を得た。

| モデル | 非正規化値の数 | その値を含む初期化テンソル数 |
| --- | ---: | ---: |
| AdaFace IR101 | 202,104 | 24 |
| R50 | 30,184 | 25 |

集計対象は元の ONNX の最上位にある密な `FLOAT` 初期化テンソルの全 float32 保存要素で、正負ゼロを除き、`0 < abs(x) < 2^-126` を数えた。ビットパターンでも、符号ビットを除いた整数が `0` と `0x00800000` の厳密な間にあることで確認できる。畳み込み重み、PReLU、BatchNorm の保存値を含み、畳み込み重みだけや学習可能パラメータだけの件数ではない。実行中の活性や顔特徴の統計でもない。読取専用監査と資産ハッシュは `denormal-weight-audit.json` に保存した。この値の存在は調査の手掛かりだが、件数だけで全時間を説明できるわけではない。

Intel の x86 浮動小数点制御レジスタ MXCSR には関連するモードがある。**FTZ** は対象命令が生成した非正規化結果をゼロにし、**DAZ** は対象命令への非正規化入力オペランドをゼロとして扱う。SSE/AVX 浮動小数点演算の意味と性能に影響し、無条件の高速化を保証するものではない。[Intel FTZ / DAZ 説明](https://www.intel.com/content/www/us/en/docs/dpcpp-cpp-compiler/developer-guide-reference/2025-1/set-the-ftz-and-daz-flags.html)

実験では元の FP32 重みファイルとハッシュを維持し、FP16 や INT8 への変換、再訓練は行っていない。ただし、**浮動小数点演算の非正規化数に対する意味は変わる**ため、ファイル不変だけで精度不変を導くことはできない。ONNX Runtime 1.29.0 は既定無効の `session.set_denormal_as_zero` を提供し、公式説明も有効化がモデル精度に影響し得ると明示する。[ORT 1.29.0 設定キー定義](https://github.com/microsoft/onnxruntime/blob/v1.29.0/include/onnxruntime/core/session/onnxruntime_session_options_config_keys.h)

### 8.2 固定 3 クロップによる制御診断

位置合わせ済みの固定 3 クロップを選び、独立ワーカーで ORT オプションを `0` と `1` に設定した。実行順は無効、有効の順だった。両バックボーンを単一スレッド、スピン無効、逐次実行とし、入力前処理は参照実装を引き継いだ。ウォームアップ後に 3 周を計測し、各構成で計 9 クロップ観測を得た。

計測は各バックボーンの `Session.run` のみを囲む。表は 9 観測の中央値である。両バックボーン合計は各クロップの 2 呼出時間の合計の中央値であり、**3 クロップ全体の総処理時間ではない**。

| kernel 範囲 | FTZ/DAZ 無効、s/クロップ | FTZ/DAZ 有効、s/クロップ | 無効時間 / 有効時間 |
| --- | ---: | ---: | ---: |
| AdaFace | 9.614829 | 0.470143 | 20.45 倍 |
| R50 | 1.857830 | 0.250646 | 7.41 倍 |
| 両バックボーンの逐次合計 | 11.470675 | 0.720563 | 15.919 倍 |

3 クロップで、両モードのバックボーン生出力、融合特徴、最終確率が全項目で同じだった。Top-1、順序付き Top-5、閾値 0.95 の受理判定も一致した。別の実行時演算プローブでも、主呼出スレッドの非正規化入力・結果の処理モード変更を確認した。

これは本機で非正規化数処理を性能要因として追加検証する直接の根拠となる。ただし、時間には検出、大画像デコード、HTTP、リクエスト待ちを含まず、対象は 3 サンプルだけである。診断プロセスの浮動小数点モードは非計測の前処理や分類にも作用するため、最終 C++ サービスの全数値動作を分離検証した結果とはいえない。固定順と 1 回の診断では実行環境の差もすべては除去できない。

### 8.3 候補コアによるスレッド浮動小数点状態の管理

Session 作成時の設定だけでは十分でない。ORT 1.29.0 は最初の呼出スレッドに一度限りの初期化を行い、Session 専用スレッドプールには別に設定を渡す。後から呼び出す任意のスレッドが必要な MXCSR 状態を自動取得するとは仮定できない。[ORT 1.29.0 Session 初期化実装](https://github.com/microsoft/onnxruntime/blob/v1.29.0/onnxruntime/core/session/inference_session.cc)

Go の goroutine と OS スレッドは固定の 1 対 1 対応ではない。スレッド局所状態を、以前の別 cgo 呼出が残した設定に依存させるべきではない。[Go のスレッド固定説明](https://pkg.go.dev/runtime#LockOSThread) そこで候補は設定、推論、復元を同じ C++ 呼出内に置いた。

1. ORT Session 作成時と各 `Model::run` のスコープ開始時に、呼出スレッドの MXCSR 全体を保存する。
2. 実験設定に応じて FTZ と DAZ を明示的に有効・無効にし、他の制御ビットを保持する。ORT Session オプションでその専用スレッドプールの方針も設定する。
3. 通常 return と例外巻き戻しの両方で、RAII guard により元の状態全体を復元する。永続 R50 ワーカーも同じ `Model::run` guard を通す。

この方法では複数 cgo 呼出の間で浮動小数点状態を維持する必要がなく、推論モードを後続 Go 呼出に残さない。画像前処理と分類ヘッドは guard の外にある。候補は `fast-math` を有効にしておらず、明示した実行範囲の浮動小数点モードを調べる実験である。

guard の `true` モードが対応するのは **Linux x86_64 で MXCSR の FTZ/DAZ が利用可能な環境**に限られる。現在の Mac ARM を含む非対応環境では有効化を明示的に拒否し、適用したようには扱わない。Linux では切替、入れ子、例外時復元、実際の非正規化演算、**8 永続スレッドからの反復呼出**の guard 検査が通過し、候補 CTest も通過した。guard テストは対象とした状態管理の挙動を示すが、ORT 全モデルの精度検証は別途必要である。

この実験中、候補は無視対象ディレクトリ内のパッチ、独立ソースコピー、独立共有ライブラリにのみ存在し、製品 `native/` ソースと元のベースライン成果物は変えていない。Go 実行ファイルは未変更ビルドを使い、候補コアと独立 JSON で実験を行った。`runtime.flush_denormals` はこのコアに追加した厳密な真偽値フィールドである。**JSON にこのキーを追加するだけで旧コアライブラリが実験処理を実行することはない。** 後続の製品統合は第 9 節を参照。

候補 C API の 3 クロップ検査では、1 顔約 **0.492 秒**だった。検出と HTTP は実行していない。特徴と確率はネイティブベースラインのキャッシュと完全一致した。Python キャッシュに対しては特徴が一致し、確率の最大絶対差は `1.1920928955078125e-7`、候補順と受理判定も同じだった。これは全量検証に進むための確認段階である。候補は 2 バックボーン並列で、C API の範囲も逐次 kernel 診断より広い。両者の時間を割って FTZ 単独で約 23 倍の高速化とすることや、HTTP 高速化とすることはできない。

### 8.6 試験後のホスト確認

全実験終了後、元サービスの `/ready` は 200 を返した。既存 10 コンテナの ID、PID、起動時刻と、4 つの保護対象マウントのデバイス番号・inode は変わらなかった。ベンチマークポートを閉じ、今回の推論ワーカーは残っていない。元ランタイムと候補成果物のハッシュを個別に再確認し、主ディスクの空きは約 **60.59 GiB** だった。
