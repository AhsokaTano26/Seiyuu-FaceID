# Intel N150 + 8 GB の Linux / Docker 構成

[English](N150.md) | [简体中文](N150.zh-CN.md) | [日本語](N150.ja.md)

既存の FP32 デュアルバックボーンと分類ヘッドを使用し、モデル、検出サイズ、位置合わせ、品質基準、0.95 の受け入れしきい値を維持します。
追加のリソース設定でスレッドスケジューリングとアロケーターを調整し、許容できる遅延とメモリ使用量を保ちながら、リクエスト当たりの CPU 時間を減らすことを目指します。

N150 は4コア/4スレッド、ベース消費電力6 Wのプロセッサーです。[Intel 仕様](https://www.intel.com/content/www/us/en/products/sku/241636/intel-processor-n150-6m-cache-up-to-3-60-ghz/specifications.html) を参照してください。
2026-10-27 時点で、対象機の主ディスク保守、Linux ネイティブビルドと起動、1,051クロップと12枚の元画像による一致性比較、3組すべての HTTP ベースライン実験を完了しました。
結果と後続の独立実験は [N150 実機報告](N150_BENCHMARK.ja.md) にあります。
以下の過去の Mac 表を N150 の遅延や消費電力として扱うことはできません。
認識原理、実行構成、保守記録の全体は [技術アーキテクチャ詳解](TECHNICAL_ARCHITECTURE.ja.md) を参照してください。

3組のベースラインでは、本ページの Python プリセットは旧スレッド構成を再現した Python に対して **CPU 時間を約34.4%削減**しましたが、平均 HTTP 所要時間は約 **37.9%増加**しました。
同一設定の C++ / Go では信頼できる高速化が見られず、ピーク RSS も増えました。
このスレッドプリセットだけでは低遅延の効果を得られません。

後続の FTZ/DAZ 最適化では全件回帰検証と3プロセスでの HTTP 計測を完了しました。
平均 HTTP 所要時間は約0.681秒、過去のホールドアウト Top-1 は98.48%を維持しました。[FTZ 実験結果](N150_BENCHMARK.ja.md#ftz-daz-follow-up) を参照してください。
2026-10-28 に `native/` へ統合し、N150 の C++ / Go systemd サービスで有効にしました。エクスポート時は `--flush-denormals` を指定します。
操作は [ネイティブデプロイとロールバック](NATIVE_CPP_GO.ja.md#linux-systemd-部署) にあります。
本ページの Python YAML / Docker コマンドは互換方式として残し、ネイティブ FTZ 経路を有効にしません。
候補とベースラインは異なる段階で測定しており、ピーク RSS は旧スレッド Python に対してなお約17.9%高い値です。
長期運用と負荷試験の受け入れは未完了です。

Docker を使わない [Linux + systemd のネイティブデプロイ](DEPLOY_NATIVE_LINUX.ja.md) にも対応します。
Linux コンテナーはホストのカーネルを共有するため、仮想マシンと同様の CPU 仮想化コストが必ず発生するわけではありません。[Docker 公式説明](https://docs.docker.com/get-started/docker-concepts/the-basics/what-is-a-container) を参照してください。
既存のモデル計算は [ONNX Runtime のネイティブ実行インターフェース](https://onnxruntime.ai/docs/api/python/api_summary.html) を通して実行しています。
Python の API 層を書き直してもデュアルバックボーンの計算量は自動的に減りません。
後に C++ / Go の Linux 実行ファイルと付随する共有ライブラリーをビルド、検証しました。実行ファイルに加えて共有ライブラリーが必要です。
コンテナーとホストの負荷差は同じ実装を用いて別途比較する必要があります。
3組の言語/スレッドベースラインは Docker 負荷の測定には該当しません。

<a id="运行配置"></a>

## 実行設定

`configs/n150.yaml` は2バックボーンの並列処理を維持し、各バックボーンの intra-op を1スレッドにします。
全 ORT セッションのスピン待機を無効にします。
検出器は `runtime.detector_intra_op_threads: 2` で元のスレッド数を維持します。
検出と認識は順次実行します。
Uvicorn は1 workerだけを動かし、認識段階の2バックボーンで主要計算スレッドを合計2本使います。

検出器だけスレッド数を維持するのは、過去の Mac 実測に基づきます。
検出器も1スレッドにすると、12枚の元画像でランドマークが最大約 `0.000183` ピクセル変化しました。
これは位置合わせの補間に影響し、一部の分類確率を約 `0.000149` 変える大きさでした。
検出器を2スレッドに保ちスピンを無効にすると、検出と全認識出力が要素ごとに一致しました。
数値許容誤差を緩めずにこの差を解消しました。

これらの設定は重みと浮動小数点精度を変更しません。
スピンを無効にすると待機中の CPU 処理を減らせますが、スレッド起床と遅延のトレードオフがあります。
[ORT スレッド説明](https://onnxruntime.ai/docs/performance/tune-performance/threading.html) を参照してください。
CPU メモリ arena は `runtime.enable_cpu_mem_arena` で別途設定でき、対象機で有効/無効を比較できます。
ほかのメモリ再利用とメモリパターン設定は ORT 既定値を維持します。

今回のコードを含む新しいイメージを使用してください。
古いイメージは追加のリソース設定を適用せず、対象機の計測ツールも含みません。
公開前はリポジトリで次のようにビルドできます。

```bash
docker build -t seiyuu-faceid:n150 .
```

`.env` の `FACEID_IMAGE` をこのイメージタグへ設定します。
サーバーで対応する Linux amd64 イメージをビルドするか、ビルド済みイメージを読み込み、元のデプロイ手順に従って API キーを設定します。
起動コマンドは次のとおりです。

```bash
docker compose -f compose.yaml -f compose.n150.yaml up -d --wait --wait-timeout 180
```

モデルと設定は引き続き読み取り専用マウントです。
上書きファイルは `configs/n150.yaml` を既存の `/app/configs/default.yaml` にマウントするため、既定ファイルを編集する必要はありません。
`docker compose -f compose.yaml up -d` で元の設定に戻せます。
設定更新後は同じ2つの `-f` 引数でサービスを再作成します。

<a id="在目标机测-cpu耗时和内存"></a>

## 対象機で CPU、所要時間、メモリを測定

計測中は別のモデルインスタンスや高負荷処理を避け、CPU 競合による結果への影響を防ぎます。
以下のコマンドは学習写真や学習特徴量を必要としません。
決定的なランダムクロップを使い、リソースと出力一致性だけを測ります。実人物の分類精度は測りません。

```bash
docker compose -f compose.yaml -f compose.n150.yaml run --rm --no-deps -T faceid \
  python /app/tools/benchmark_target.py --config /app/configs/default.yaml \
  --synthetic --samples 8 --runs 5 --warmups 2 --repeats 2 \
  --output /tmp/n150-benchmark.json > n150-benchmark.json
```

設定ごと、繰り返しごとに新規プロセスを作り、ピーク RSS を比較可能にします。
同じ入力で元の順次/並列設定、スピン無効、1/2/4スレッド、CPU arena を比較します。
レポートにはクロップ分類1枚当たりの平均/P95 wall time、CPU 時間、起動時間、プロセスのピーク RSS、短い待機区間の CPU 時間、ベースラインに対する出力一致性を記録します。
検出器は読み込みます。計測時間は検出、HTTP、画像デコード、リクエスト待機を含みません。

CPU ミリ秒/枚は CPU の処理量を表し、電力量やマシン全体の消費電力を示しません。
平均使用コア数は CPU 時間を wall time で割った値です。
ピーク RSS は Python、全読み込み済みモデル、ウォームアップを含み、モデルファイルサイズや Docker 全体のメモリ使用量とは集計範囲が異なります。
実際の位置合わせ済み顔を使う場合は、そのディレクトリを自分でコンテナーにマウントし、`--crop-dir /path` のパスを指定し直します。
入力は112×112が必要です。ベンチマークは自動アップロードや学習ディレクトリの読み込みを行いません。

設定選択時は最速値だけで決めず、CPU 時間、P95、RSS を合わせて比較します。
8 GBホストでは OS とアップロード画像のデコード用に余裕を残します。
実運用中に `docker stats --no-stream` でコンテナー使用量を確認します。
集合写真と高解像度画像には別途実 API リクエストのテストが必要です。

## ローカルのリソース比較（N150 以外）

測定環境は macOS ARM64、ONNX Runtime 1.29.0 です。
各設定で独立プロセスを2回使用し、固定ランダムクロップ8枚、各5回実行、ウォームアップ2回で測定しました。
全設定で検出器を2スレッドに固定しています。
表は2プロセスの平均値の中央値で、全モデル読み込み後のプロセスピーク RSS を含みますが検出器は実行していません。
対象機の性能を予測するデータではありません。

| 設定 | 平均 wall time/枚 | CPU 時間/枚 | ピーク RSS |
| --- | ---: | ---: | ---: |
| 元の順次処理、各バックボーン2スレッド、スピン有効 | 79.23 ms | 179.18 ms | 906.90 MiB |
| 前回の並列処理、各バックボーン2スレッド、スピン有効 | 53.23 ms | 192.09 ms | 932.77 MiB |
| **CPU 節約プリセット、各バックボーン1スレッド並列、スピン無効** | **57.05 ms** | **101.62 ms** | **928.95 MiB** |
| 低遅延候補、各バックボーン2スレッド並列、スピン無効 | 51.89 ms | 181.47 ms | 931.28 MiB |
| CPU 節約プリセットで arena も無効 | 55.89 ms | 100.35 ms | 911.52 MiB |

前回の並列設定に対し、CPU 節約プリセットは **CPU 時間を47.1%削減**し、平均 wall time は **3.81 ms（7.2%）増加**しました。
短い待機区間の CPU 時間は約0.07 msです。
2つの指標にトレードオフがあるため、同時に47%高速化したとは表現できません。
arena 無効化はピークを約17 MiB減らしただけで、効果は小さく対象機では未検証です。
そのため既定の arena を維持し、対象機で再比較できるようにしています。

遅延をさらに調べる場合は、`configs/n150.yaml` の `intra_op_threads: 2` だけを変更した別候補を測定できます。
Mac では前回の並列設定に対して **wall time を約2.5%、CPU 時間を5.5%削減**しました。
今回の N150 3組ベースラインでは、この「2スレッド並列、スピン無効」候補を測定していないため、対象機で別途計測が必要です。
8組すべての生記録はローカルの無視対象ファイル `data/experiments/n150-resource-final-20261027.json` にあります。
初回の探索記録は `n150-resource-20261027.json` です。

## 精度の適用範囲

過去の Mac 検証では、CPU 節約と低遅延候補の各設定で、過去のホールドアウト **1,051クロップ**すべての特徴量を再抽出しました。
特徴量、分類確率、Top-1、Top-5 順序、0.95 の受け入れ結果は現在の設定と全要素が完全一致しました。
Top-1 は **1,035/1,051＝98.48%** を維持しました。
さらに **元画像12枚/検出顔14件**を測定し、検出器を2スレッドに保つと全出力が要素ごとに一致しました。
モデル ID と重みのチェックサムも維持しています。
確認記録は `data/experiments/n150-validation-20261027/verification.json` です。

後に N150 の CPU 節約設定で Python と C++ を同じ規模で比較しました。
Top-1、Top-5 順序、0.95 の受け入れ判定はすべて一致しましたが、浮動小数点特徴量と確率はビット単位の一致ではありません。
[実機精度記録](N150_BENCHMARK.ja.md#accuracy-and-parity) を参照してください。
全クロップ比較は N150 設定を対象にしています。
旧スレッド組は別途12枚の HTTP 元画像で検証し、全クロップ比較は再実行していません。
過去データはモデル選択に利用済みで、新しい独立した汎化保証は得られません。
12枚の元画像もすべての形式と境界入力を網羅しません。

INT8、FP16、モデル蒸留、バックボーン置換は、今回の精度不変を保証した最適化には含めません。
さらに計算量を減らせる可能性はありますが、独立した校正と評価が必要です。
OpenVINO などの実行バックエンドも、接続可能な Intel ホストで個別に検証してください。

リソース設定段階の検証では **186テストが成功**し、Ruff、コンパイル、差分の空白検査も成功しました。
Compose 設定のマージ、デプロイパッケージの許可リスト、実モデルの検証も成功しています。
テストには既存の Starlette/httpx/AnyIO 非推奨警告が2件ありました。
この段階ではローカル Docker daemon が停止中で、対象機にも未接続でした。
これらの過去の検査は Linux イメージの実行や systemd サービス起動の実証にはなりません。
後続のネイティブ移行時の Mac 検証は [C++ / Go 記録](NATIVE_CPP_GO.ja.md)、N150 で実際に行ったビルド、テスト、精度、3組の HTTP 確認は [実機報告](N150_BENCHMARK.ja.md) を参照してください。
2026-10-28 の本番切り替えは同報告の第9節に分けて記載しています。長期負荷試験の受け入れは未完了です。
