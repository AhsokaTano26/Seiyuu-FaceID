# HTTP API implementation plan

[English](2026-10-21-http-api.md) | [简体中文](2026-10-21-http-api.zh-CN.md) | [日本語](2026-10-21-http-api.ja.md)

This file records the 2026-10-21 plan. Agentic workers followed superpowers:executing-plans task by task.

The goal was to let callers upload images over HTTP and receive structured face detection and identity classification results.

A FastAPI factory loads FaceIdEngine once during lifespan. Upload validation and decoding are separate, HTTP schemas are explicit, and inference is serialized in a thread pool. Reuse the pipeline, keeping training, weights, web behavior and existing uncommitted work intact.

The stack is FastAPI, Uvicorn, python-multipart, Pillow and httpx for tests. The user requested the API document before implementation, recorded in `docs/API.md`.

## Global constraints

- The API extra is optional. Existing Python/CLI/web callers run with their own dependencies.
- Retain uncommitted changes and work in the current directory without Git commits or worktree migration.
- Accept JPEG/PNG/WebP, at most 10 MiB per file, 81 MiB per request, 20,000,000 pixels, and 1–8 images per batch.
- Default top_k and probability_threshold follow configuration, currently 5 and 0.95.
- Error responses protect model/key/path details. Pass inference parameters per request, keeping shared configuration fixed.

## Review focus

- Interrupted uploads exceeding total size still return unified 413 with no Content-Length.
- EXIF coordinates are consistent, and oversized inputs are rejected before full decoding.
- Mixed batches preserve order and continue valid items. Model failures are server errors.
- Missing models fail startup with diagnosable logs. HTTP 500 protects internal paths. Health stays responsive during inference.
- Concurrent requests cannot mutate top_k or thresholds or accumulate parallel inference memory.
