# 分類精度と速度の最適化記録（2026-10-27）

[English](CLASSIFIER_OPTIMIZATION.md) | [简体中文](CLASSIFIER_OPTIMIZATION.zh-CN.md) | [日本語](CLASSIFIER_OPTIMIZATION.ja.md)

今回、配備済みの分類ヘッドを維持し、AdaFace/R50 の並列推論を有効にした。分類ヘッドの探索では既存モデルを置き換える価値のある結果は得られなかった。並列実行によって本機の特徴抽出遅延が短縮され、特徴の順序、モデルの重み、受理閾値 0.95 は維持された。

## 速度

本機の ONNX Runtime CPU を使い、開発プールから異なる出典グループのクロップを 16 枚固定して抽出し、各クロップを 3 回反復した。逐次実行と並列実行を交互に行い、それぞれ個別にウォームアップした。分類ヘッドの確率比較は計測区間外で行った。

| 各バックボーンの intra-op スレッド数 | 逐次平均時間 | 並列平均時間 | 逐次／並列の時間比 |
| --- | ---: | ---: | ---: |
| 1 | 101.31 ms | 56.40 ms | 1.80 |
| 2 | 78.39 ms | 54.22 ms | 1.45 |
| 4 | 58.42 ms | 40.47 ms | 1.44 |

各バックボーン 2 スレッドという既存設定を維持する構成を採用し、平均特徴抽出遅延を **30.8%** 削減した。この設定の P95 は 86.32 ms から 61.04 ms に低下した。3 種類のスレッド設定それぞれで、逐次／並列の出力は全要素が一致し、抽出確認した Top-1 も各 48/48 件で一致した。4 スレッドの結果に基づく既定スレッド数の変更は行っていない。本機環境は macOS 26.6.2、ARM64、ONNX Runtime 1.29.0 だった。

計測範囲は位置合わせ済みクロップからの 2 バックボーン特徴抽出であり、画像デコード、顔検出、品質検査、HTTP オーバーヘッドは含まない。API 全体のスループット向上を示す値としては扱わない。本機で得られた結果であり、Linux や CPU クォータの異なる環境では再計測が必要になる。

設定項目は `runtime.parallel_backbones`。同梱の `configs/default.yaml` は `true` に設定されている。この項目のない旧設定では逐次モードを維持する。各モデルの intra-op は 2 スレッドで、並列時には合計約 4 計算スレッドを使用する。資源が限られる場合は `false` にできる。実行器は継続して再利用し、API 終了時に明示的に解放する。片方のバックボーンが失敗した場合も、両タスクの完了を待ってから例外を伝播する。

実際のランタイムへの組み込み後、**歴史的ホールドアウトの全 1,051 クロップ**で元の逐次計算と新しい並列計算を交互に実行した。

- 特徴と分類確率は全要素が完全に一致した。Top-1 と閾値 0.95 の受理／要確認判定も過去の記録と一致した。
- Top-1 は **1,035/1,051＝98.48%**、Top-5 は 99.14%、Macro-F1 は 99.10% のままだった。配備済み分類ヘッドの SHA-256 は変わっていない。
- 全件の平均特徴抽出時間は **77.61 → 52.12 ms（32.8% 削減）**、P95 は **79.35 → 55.40 ms** だった。これもクロップ単位の特徴抽出時間であり、最初の観測を含み、検出と HTTP は含まない。
- 新たに抽出した特徴と保存済みの凍結特徴の最大差は `9.16e-7`、確率と過去の保存値との最大差は `3.52e-6` だった。これらの過去値との数値差は逐次と並列で完全に同じで、個人識別や受理結果は変わらなかった。

## 分類ヘッドの実験

データは確認済み顔 5,115 枚、50 人からなる。元の訓練集合と検証集合を統合し、4,064 開発サンプルとした。歴史的テストの 1,051 枚は、今回の訓練、標準化、候補選択には使用していない。

開発プールには 2,513 の出典成分がある。`sample_id`、`source_group`、原画像 SHA、クロップ SHA、任意の写真集グループを統合し、推移的重複関係と開発／テスト分離を検査した。2 人はそれぞれ出典成分が 1 つしかなく、常に訓練に入れ、OOF 指標から除外した。このため OOF の対象は 4,062 枚、48 人となる。各 fold の訓練には全 50 人を含む。

候補一覧と選択規則は実行前に保存した。

- 標準化 LR は C 6 通り × クラス重み 2 通り × AdaFace/R50 重み 3 通りの計 36 構成。
- 標準化なし LR は C 4 通り × クラス重み 2 通りの計 8 構成。
- 出典成分を等重みとする LR は C 3 通り × クラス重み 2 通りの計 6 構成。クラス平衡は成分数で計算し、クロップ数に基づく重みの重複適用を避けた。

3 fold を出典成分単位で分離し、前処理はその時点の訓練 fold のみで適合した。統合 OOF Top-1、対象クラスの Macro-F1、対数損失の順に比較し、最後の同点処理には固定候補順を使った。選択した設定を先に保存し、その候補とベースラインだけを後から確認した。後続結果に基づく別候補への切り替えは行っていない。

選ばれたのは標準化 LR で、`C=0.1`、`class_weight=balanced`、AdaFace 重み 0.75 だった。ブロック重みは標準化後に適用し、出力するスケーリングパラメータに組み込んだ。既存の NumPy ランタイムが直接読み取れる。出力確率と訓練実装の最大誤差は 0 だった。

| 評価範囲 | 現行ヘッド | 新候補 |
| --- | ---: | ---: |
| 選択用 OOF、シード 20261027 | 3,977/4,062（97.91%） | 3,986/4,062（98.13%） |
| 第 2 分割 OOF、シード 20261028 | 3,981/4,062（98.01%） | 3,988/4,062（98.18%） |
| 歴史的テスト Top-1 | 1,035/1,051（98.48%） | 1,033/1,051（98.29%） |
| 歴史的テストの出典成分マクロ平均正解率 | 98.65% | 98.36% |
| 歴史的テスト Macro-F1、真値のある 49 人 | 99.10% | 96.96% |
| 歴史的テストの閾値 0.95 での受理数 | 1,011 | 986 |
| うち誤受理数 | 4 | 4 |

候補は現行ヘッドの過去の誤り 16 件を修正できず、さらに 2 件の誤りを増やした。人手確認の対象は 40 枚から 65 枚に増えたため、元の分類ヘッドを維持した。

50 候補が同じ OOF を共有するため、最良 OOF スコアには選択バイアスがある。第 2 分割も同じサンプルを再利用しており、独立テストにはならない。歴史的テスト集合も以前のモデル選択に使われたため、今回の数字は探索的比較にとどまり、新たな汎化性能の証明とはいえない。歴史的テストには 676 出典成分があり、そのうち 5 成分に 380 枚の顔が含まれる。このため成分マクロ平均指標も記録し、各クロップを独立サンプルとして扱っていない。対応のある成分 bootstrap を 10,000 回、シード 20261029 で実行したところ、候補の Top-1 変化の記述的 95% 区間は −0.545 ～ 0.000 パーセントポイントだった。以前の選択バイアスを補正するものではない。

未知人物やキャラクター画像の拒否について、真値付きデータは追加しておらず、関連精度の改善も主張しない。今後の精度改善では独立した出典の確認済み写真と新しいテスト集合を補充し、特徴や分類器の変更を検証する必要がある。

## 再現とローカル証拠

```bash
uv run --extra training python tools/optimize_classifier.py --output data/experiments/new-head-search
uv run python tools/benchmark_classifier.py --threads 1 2 4 --output data/experiments/new-speed.json
uv run python tools/evaluate.py --reextract
uv run pytest
uv run ruff check .
```

出力先は未作成のパスである必要がある。モデルと詳細実験データは引き続き無視対象ディレクトリに置き、リポジトリや Release に含めない。

- `data/experiments/classifier-search-20261027/` にプロトコル、候補記録、固定設定、確認結果、独立候補ヘッド、過去の確率、比較結果を保存。
- `data/experiments/classifier_speed_20261027.json` に開発クロップの交互計測と全要素一致の確認を保存。
- `data/experiments/runtime-parallel-20261027/` に実際の並列ランタイムによる全ホールドアウト確認スクリプトと結果を保存。

コード検証では 131 テスト、Ruff、`git diff --check` が通過した。テストは成分リーク、単一成分の人物、過去の特徴に左右されない候補選択、出力一致、実際の 2 スレッド重複実行、例外伝播前の待機、繰り返し終了、API 資源解放を対象とする。出力には既存の Starlette/httpx/AnyIO 非推奨警告が 2 件あった。

実験手法は [scikit-learn のグループ交差検証](https://scikit-learn.org/stable/modules/cross_validation.html) を参照した。各モデルのスレッド数と CPU 資源のトレードオフは [ONNX Runtime のスレッド管理](https://onnxruntime.ai/docs/performance/tune-performance/threading.html) を参照した。
