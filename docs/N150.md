# Intel N150 + 8 GB：Linux / Docker

使用原有 FP32 双骨干和分类头，模型、检测尺寸、对齐、质量门槛和 0.95 接受阈值不变。新增资源配置会调整线程调度和分配器，目标是降低每次请求消耗的 CPU 时间，同时保持可接受的延迟与内存占用。

N150 是 4 核／4 线程、6 W 基础功耗的处理器，详见 [Intel 规格](https://www.intel.com/content/www/us/en/products/sku/241636/intel-processor-n150-6m-cache-up-to-3-60-ghz/specifications.html)。截至 2026-10-27，目标机已完成主盘维护、Linux 原生构建和启动、1,051 张裁剪与 12 张原图的一致性对照，以及完整三组 HTTP 基线实验。结果与后续独立实验见 [N150 实机报告](N150_BENCHMARK.md)；下文的 Mac 历史表格仍不能当作 N150 延迟或功耗结果。完整识别原理、运行架构和维护记录见 [技术框架详解](TECHNICAL_ARCHITECTURE.md)。

三组基线中，本页 Python 预设相对复现旧线程配置的 Python 减少约 **34.4% CPU 时间**，但平均 HTTP 耗时增加约 **37.9%**；同配置 C++ / Go 没有显示可靠提速，峰值 RSS 更高。单靠该线程预设不能获得低延迟收益。

后续 FTZ/DAZ 优化完成全量回归及三个进程的 HTTP 测量，平均 HTTP 耗时约 0.681 秒，历史留出 Top-1 仍为 98.48%，见 [FTZ 实验结果](N150_BENCHMARK.md#8-ftz--daz-独立跟进实验)。2026-10-28 已集成至 `native/` 并在 N150 启用，使用 C++ / Go systemd 服务，导出时加 `--flush-denormals`。操作见 [原生部署与回退](NATIVE_CPP_GO.md#linux-systemd-部署)。本页 Python YAML / Docker 命令仍作为兼容方案，不会启用原生 FTZ 路径。候选与基线是分阶段测量，相对旧线程 Python 的峰值 RSS 仍高约 17.9%；长期和压力场景仍待验收。

也支持[原生 Linux + systemd 部署](DEPLOY_NATIVE_LINUX.md)，无需 Docker。Linux 容器共享宿主机内核，并不必然存在虚拟机那样的 CPU 虚拟化成本，见 [Docker 官方说明](https://docs.docker.com/get-started/docker-concepts/the-basics/what-is-a-container)。现有模型计算通过 [ONNX Runtime 原生执行接口](https://onnxruntime.ai/docs/api/python/api_summary.html)完成；重写 Python 的 API 层不会自动减少双骨干的计算量。后续已构建并验证 C++ / Go Linux 可执行文件及配套共享库，它不是静态单文件程序。容器与宿主机的开销仍需保持同一实现单独比较，三组语言与线程基线不构成 Docker 开销测试。

## 运行配置

`configs/n150.yaml` 保留两骨干并行，每骨干仅一个 intra-op 线程，关闭所有 ORT 会话的线程自旋。检测器通过 `runtime.detector_intra_op_threads: 2` 保留原有线程数；检测和识别依次执行。只运行一个 Uvicorn worker，识别阶段两个骨干合计使用两个主要计算线程。

单独保留检测器线程数有此前 Mac 实测原因：将它也改为一个线程时，12 张原图上的关键点最大变化约 `0.000183` 像素，足以影响对齐插值，使个别分类概率变化约 `0.000149`。保持检测器 2 线程并关闭自旋后，检测和完整识别输出恢复逐项一致。因此没有通过放宽数值容差忽略这项差异。

这些设置不改变权重和浮点精度。关闭自旋可以减少等待阶段的 CPU 工作，但会涉及线程唤醒与延迟取舍；参见 [ORT 线程说明](https://onnxruntime.ai/docs/performance/tune-performance/threading.html)。CPU 内存 arena 另设 `runtime.enable_cpu_mem_arena`，可用目标机基准比较开关；其他内存复用和内存模式维持 ORT 默认。

使用包含本次代码的新镜像；旧镜像不会应用新增的资源配置项，也不包含目标机测速工具。镜像发布前可在仓库构建：

```bash
docker build -t seiyuu-faceid:n150 .
```

在 `.env` 将 `FACEID_IMAGE` 设置为这个镜像标签（服务器上需构建对应的 Linux amd64 镜像，或导入已构建镜像），并按原部署说明设置 API 密钥。启动命令：

```bash
docker compose -f compose.yaml -f compose.n150.yaml up -d --wait --wait-timeout 180
```

模型和配置仍然只读挂载。覆盖文件将 `configs/n150.yaml` 挂到已有 `/app/configs/default.yaml` 位置；无需修改默认配置。恢复原配置可使用 `docker compose -f compose.yaml up -d`。更新配置后使用相同的两个 `-f` 参数重建服务。

## 在目标机测 CPU、耗时和内存

测速时避免同时运行另一个模型实例或其他重负载，以免 CPU 竞争污染结果。下列命令不需要训练照片或训练特征，使用确定性的随机裁剪，仅衡量资源与输出一致性，不衡量真人分类准确率：

```bash
docker compose -f compose.yaml -f compose.n150.yaml run --rm --no-deps -T faceid \
  python /app/tools/benchmark_target.py --config /app/configs/default.yaml \
  --synthetic --samples 8 --runs 5 --warmups 2 --repeats 2 \
  --output /tmp/n150-benchmark.json > n150-benchmark.json
```

每个配置、每次重复都创建新进程，使峰值 RSS 可比较；以固定输入比较原顺序／并行配置、关闭自旋、1/2/4 线程与 CPU arena。报告记录每张裁剪分类的平均／P95 wall time、CPU 时间、启动耗时、进程峰值 RSS、短暂空闲窗口 CPU 和相对基线的输出一致性。检测器会加载，计时范围不包含检测、HTTP、图片解码或请求排队。

CPU 毫秒／张衡量 CPU 工作量，不等于电量或整机功耗；平均占用核数为 CPU 时间除以 wall time。峰值 RSS 包括 Python、所有已加载模型和预热，不等于模型文件大小，也不等于 Docker 的全部内存占用。若需使用实际已对齐人脸，在容器自行挂载该目录，改用 `--crop-dir /路径`；输入必须为 112×112，基准不会自动上传或读取训练目录。

选配置时同时比较 CPU 时间、P95 和 RSS，不能只选最快一项。对于 8 GB 主机保留系统及上传解码空间；按实际运行 `docker stats --no-stream` 检查容器占用。合照和高分辨率上传还需另做真实 API 请求测试。

## 本地资源对照（非 N150 数据）

macOS ARM64，ONNX Runtime 1.29.0；每组两次独立进程，8 张固定随机裁剪，每张运行 5 次、预热 2 次，所有配置均固定检测器 2 线程。表中为两次进程平均值的中位数，包含全部模型加载后的进程峰值 RSS，但没有运行检测器。这不是目标机性能预测。

| 配置 | 平均 wall time／张 | CPU 时间／张 | 峰值 RSS |
| --- | ---: | ---: | ---: |
| 原顺序：每骨干 2 线程、自旋开 | 79.23 ms | 179.18 ms | 906.90 MiB |
| 上一轮并行：每骨干 2 线程、自旋开 | 53.23 ms | 192.09 ms | 932.77 MiB |
| **省 CPU 预设：每骨干 1 线程并行、自旋关** | **57.05 ms** | **101.62 ms** | **928.95 MiB** |
| 延迟候选：每骨干 2 线程并行、自旋关 | 51.89 ms | 181.47 ms | 931.28 MiB |
| 省 CPU 预设另关 arena | 55.89 ms | 100.35 ms | 911.52 MiB |

相对上一轮并行配置，省 CPU 预设减少 **47.1% CPU 时间**，平均 wall time 增加 **3.81 ms（7.2%）**；短暂空闲窗口 CPU 约 0.07 ms。两个方向存在取舍，不能称为同时提速 47%。关闭 arena 只减少约 17 MiB 峰值，资源收益较小且未在目标机验证，因此暂保留默认 arena，供目标机再比较。

如果进一步探索延迟，可把 `configs/n150.yaml` 的 `intra_op_threads: 2`、其他项不变作为另一个待测候选。Mac 上此配置相对上一轮减少约 **2.5% wall time、5.5% CPU 时间**；本轮 N150 三组基线没有测试这个“两线程并行、关自旋”候选，在目标机仍须单独测量。完整八组原始记录保存在本机忽略目录 `data/experiments/n150-resource-final-20261027.json`，初轮探索记录为 `n150-resource-20261027.json`。

## 精度边界

此前 Mac 上已对省 CPU 和低延迟候选两种配置分别重新提取全部 **1,051 张**历史留出裁剪：特征、分类概率、Top-1、Top-5 顺序和 0.95 接受结果均与当前配置逐项完全一致。Top-1 保持 **1,035/1,051＝98.48%**。另测 **12 张原图／14 张检测人脸**，保留检测器 2 线程后完整输出逐项一致，模型 ID 和权重校验不变。复核记录为 `data/experiments/n150-validation-20261027/verification.json`。

后续在 N150 上完成了省 CPU 配置下 Python 与 C++ 的同规模对照，Top-1、Top-5 顺序和 0.95 接受判定全部一致，但浮点特征与概率并非逐位相同，详见 [实机准确率记录](N150_BENCHMARK.md#4-已完成的准确率与一致性结果)。全量裁剪对照覆盖 N150 配置；旧线程组另在 12 张 HTTP 原图上验证，没有重新完成全量裁剪对照。历史数据曾参与模型选择，不能提供新独立泛化保证；12 张原图也不能覆盖全部图片格式和边界输入。

本次不把 INT8、FP16、模型蒸馏或替换骨干作为已保证准确率不变的优化。它们可能进一步降低计算量，但需要独立校准与评估；OpenVINO 等执行后端也应在可访问的 Intel 主机上单独验证。

资源配置阶段的代码验证记录：**186 项测试通过**，Ruff、编译和差异空白检查通过；Compose 配置合并、部署包白名单和实际模型校验通过。测试有两条现存的 Starlette/httpx/AnyIO 弃用警告。该阶段本机 Docker daemon 未运行，目标机当时尚未连接，因此这些历史检查不代表 Linux 镜像实跑或 systemd 服务启动。后续原生迁移的 Mac 验证见 [C++ / Go 记录](NATIVE_CPP_GO.md)，N150 实际执行的构建、测试、准确率与三组 HTTP 检查见 [实机报告](N150_BENCHMARK.md)。2026-10-28 的生产切换单列于该报告第 9 节，长期压力验收尚未完成。
