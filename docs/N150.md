# Intel N150 + 8 GB on Linux / Docker

[English](N150.md) | [简体中文](N150.zh-CN.md) | [日本語](N150.ja.md)

This configuration uses the existing FP32 dual backbones and classification head.
Models, detection dimensions, alignment, quality gates, and the 0.95 acceptance threshold remain unchanged.
The added resource configuration adjusts thread scheduling and allocation to reduce CPU time per request while keeping latency and memory usage acceptable.

The N150 has 4 cores, 4 threads, and 6 W processor base power. See [Intel specifications](https://www.intel.com/content/www/us/en/products/sku/241636/intel-processor-n150-6m-cache-up-to-3-60-ghz/specifications.html).
By 2026-10-27, the target host had completed main-disk maintenance, native Linux build and startup, consistency comparisons on 1,051 crops and 12 original images, and all three HTTP baseline experiments.
Results and subsequent independent experiments are in the [N150 hardware report](N150_BENCHMARK.md).
The historical Mac table below does not measure N150 latency or power consumption.
See the [technical architecture](TECHNICAL_ARCHITECTURE.md) for recognition principles, runtime architecture, and maintenance records.

In the three baselines, this page's Python preset reduced **CPU time by approximately 34.4%** relative to Python reproducing the old thread configuration, while average HTTP duration increased by approximately **37.9%**.
C++ / Go with the same configuration showed no reliable speedup and used higher peak RSS.
This thread preset alone does not provide a low-latency improvement.

Subsequent FTZ/DAZ optimization completed full regression checks and HTTP measurements across three processes.
Mean HTTP duration was approximately 0.681 seconds, with historical holdout Top-1 remaining 98.48%. See the [FTZ experiment results](N150_BENCHMARK.md#ftz-daz-follow-up).
On 2026-10-28, this was integrated into `native/` and enabled on N150 through a C++ / Go systemd service. Add `--flush-denormals` when exporting.
See [native deployment and rollback](NATIVE_CPP_GO.md#linux-systemd-部署) for procedures.
This page's Python YAML / Docker commands remain a compatible option and do not enable the native FTZ path.
The candidate and baselines were measured at separate stages. Peak RSS remains approximately 17.9% higher than old-thread Python.
Long-running and stress scenarios still await acceptance testing.

[Native Linux + systemd deployment](DEPLOY_NATIVE_LINUX.md) is also supported without Docker.
Linux containers share the host kernel, so virtual-machine-style CPU virtualization costs are not inherent. See [Docker's explanation](https://docs.docker.com/get-started/docker-concepts/the-basics/what-is-a-container).
Current model computation already runs through [ONNX Runtime's native execution interface](https://onnxruntime.ai/docs/api/python/api_summary.html).
Rewriting the Python API layer does not automatically reduce computation in the two backbones.
C++ / Go Linux executables and accompanying shared libraries have subsequently been built and verified. Shared libraries are required alongside the executable.
Container and host overhead still requires a separate comparison using the same implementation.
The three language/thread baselines do not measure Docker overhead.

## Runtime configuration

`configs/n150.yaml` retains parallel backbones, with one intra-op thread per backbone, and disables thread spinning for every ORT session.
The detector retains its original thread count through `runtime.detector_intra_op_threads: 2`.
Detection and recognition run sequentially.
Only one Uvicorn worker runs, and the two recognition backbones together use two main compute threads.

The separate detector thread count follows earlier Mac measurements.
Reducing it to one thread changed landmarks by up to approximately `0.000183` pixels across 12 original images.
That was enough to affect alignment interpolation and change individual class probabilities by approximately `0.000149`.
Keeping 2 detector threads and disabling spinning restored element-by-element equality in detection and complete recognition output.
The discrepancy was resolved without relaxing numerical tolerances.

These settings change neither weights nor floating-point precision.
Disabling spinning reduces CPU work while waiting, with tradeoffs in thread wakeup and latency.
See [ORT threading documentation](https://onnxruntime.ai/docs/performance/tune-performance/threading.html).
CPU memory arena behavior is configured separately with `runtime.enable_cpu_mem_arena` and can be compared on the target host.
Other memory reuse and memory pattern settings retain ORT defaults.

Use a new image containing this code. Old images do not apply the added resource options and omit the target-host benchmark tool.
Before image publication, build it in the repository.

```bash
docker build -t seiyuu-faceid:n150 .
```

Set `FACEID_IMAGE` in `.env` to that image tag.
Build the corresponding Linux amd64 image on the server or import an already built image, and configure the API key following the deployment instructions.
Start with the following command.

```bash
docker compose -f compose.yaml -f compose.n150.yaml up -d --wait --wait-timeout 180
```

Models and configuration remain mounted read-only.
The override mounts `configs/n150.yaml` at the existing `/app/configs/default.yaml` location, so the default configuration file needs no edits.
Restore the original configuration with `docker compose -f compose.yaml up -d`.
After configuration changes, recreate the service using the same two `-f` arguments.

## Measure CPU, duration, and memory on the target host

Avoid another model instance or heavy workload during benchmarking so CPU contention does not distort results.
The following command requires no training photos or features.
It uses deterministic random crops to measure resource use and output consistency only. It does not measure classification accuracy on real people.

```bash
docker compose -f compose.yaml -f compose.n150.yaml run --rm --no-deps -T faceid \
  python /app/tools/benchmark_target.py --config /app/configs/default.yaml \
  --synthetic --samples 8 --runs 5 --warmups 2 --repeats 2 \
  --output /tmp/n150-benchmark.json > n150-benchmark.json
```

Each configuration and repetition starts a new process so peak RSS can be compared.
Fixed inputs compare the original sequential and parallel configurations, disabled spinning, 1/2/4 threads, and the CPU arena.
The report records mean and P95 wall time per crop classification, CPU time, startup duration, peak process RSS, CPU time during a brief idle window, and output consistency relative to the baseline.
The detector is loaded. Timings exclude detection, HTTP, image decoding, and request queueing.

CPU milliseconds per image measure CPU work and do not measure electricity or total system power.
Average occupied core count is CPU time divided by wall time.
Peak RSS includes Python, all loaded models, and warmup. Its scope differs from model file size and total Docker memory usage.
To use real aligned faces, mount that directory into the container and switch to `--crop-dir /path`, replacing the path placeholder.
Inputs must be 112×112. The benchmark does not automatically upload data or read training directories.

Compare CPU time, P95, and RSS together when selecting a configuration.
Leave room for the OS and upload decoding on an 8 GB host.
Use `docker stats --no-stream` during actual operation to inspect container usage.
Group photos and high-resolution uploads also require separate real API request tests.

## Local resource comparison excluding N150 data

These measurements used macOS ARM64 and ONNX Runtime 1.29.0.
Each configuration ran in two independent processes with 8 fixed random crops, 5 runs per crop, and 2 warmups.
The detector was fixed at 2 threads in every configuration.
The table shows medians of the two process means and includes peak RSS after all models were loaded, although the detector never ran.
These results do not predict target-host performance.

| Configuration | Mean wall time/image | CPU time/image | Peak RSS |
| --- | ---: | ---: | ---: |
| Original sequential, 2 threads/backbone, spinning enabled | 79.23 ms | 179.18 ms | 906.90 MiB |
| Previous parallel, 2 threads/backbone, spinning enabled | 53.23 ms | 192.09 ms | 932.77 MiB |
| **CPU-saving preset, parallel with 1 thread/backbone, spinning disabled** | **57.05 ms** | **101.62 ms** | **928.95 MiB** |
| Latency candidate, parallel with 2 threads/backbone, spinning disabled | 51.89 ms | 181.47 ms | 931.28 MiB |
| CPU-saving preset with arena also disabled | 55.89 ms | 100.35 ms | 911.52 MiB |

Relative to the previous parallel configuration, the CPU-saving preset reduced **CPU time by 47.1%** and increased mean wall time by **3.81 ms (7.2%)**.
CPU time in the brief idle window was approximately 0.07 ms.
This is a tradeoff between two measures and cannot be described as a simultaneous 47% speedup.
Disabling the arena reduced peak memory by only about 17 MiB.
The resource benefit was small and unverified on the target host, so the default arena remains enabled for further target-host comparison.

For further latency exploration, set `intra_op_threads: 2` in `configs/n150.yaml` with other settings unchanged as another candidate.
On Mac it reduced **wall time by approximately 2.5% and CPU time by 5.5%** relative to the previous parallel configuration.
The three N150 baselines did not test this two-thread parallel candidate with spinning disabled. It still requires separate target-host measurement.
All eight original records are in the local ignored file `data/experiments/n150-resource-final-20261027.json`.
The initial exploration record is `n150-resource-20261027.json`.

## Accuracy limits

Earlier Mac validation re-extracted all **1,051 historical holdout crops** for both the CPU-saving and low-latency candidate configurations.
Features, class probabilities, Top-1, Top-5 ordering, and 0.95 acceptance results were all exactly equal element by element to the current configuration.
Top-1 remained **1,035/1,051 = 98.48%**.
A further **12 original images / 14 detected faces** produced identical complete outputs after retaining 2 detector threads.
Model IDs and weight checksums were unchanged.
The verification record is `data/experiments/n150-validation-20261027/verification.json`.

Subsequent N150 comparison used the same scale of data for Python and C++ under the CPU-saving configuration.
Top-1, Top-5 ordering, and 0.95 acceptance decisions all matched, but floating-point features and probabilities were not bitwise identical.
See the [hardware accuracy record](N150_BENCHMARK.md#accuracy-and-parity).
The full crop comparison covered the N150 configuration.
The old-thread group was separately verified on 12 HTTP original images and did not repeat the full crop comparison.
Historical data participated in model selection and cannot provide a new independent generalization guarantee.
The 12 originals also do not cover all image formats and boundary inputs.

INT8, FP16, distillation, and backbone replacement are not treated here as optimizations with guaranteed unchanged accuracy.
They may further reduce computation but need independent calibration and evaluation.
Execution backends such as OpenVINO also need separate verification on an accessible Intel host.

The resource-configuration stage recorded **186 passing tests**, plus successful Ruff, compilation, and whitespace checks.
Compose merging, deployment bundle allowlists, and actual model validation also passed.
Tests reported two existing Starlette/httpx/AnyIO deprecation warnings.
The local Docker daemon was not running at that stage, and the target host was not yet connected.
Those historical checks do not demonstrate an actual Linux image run or systemd startup.
For later native-migration verification on Mac, see the [C++ / Go record](NATIVE_CPP_GO.md).
For builds, tests, accuracy, and all three HTTP groups actually executed on N150, see the [hardware report](N150_BENCHMARK.md).
The 2026-10-28 production switch is documented separately in section 9 of that report. Long-term stress acceptance remains incomplete.
