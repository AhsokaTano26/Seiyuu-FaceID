# CI/CD の3つのデプロイ方式とモデル公開

[English](CI_CD.md) | [简体中文](CI_CD.zh-CN.md) | [日本語](CI_CD.ja.md)

ワークフローは [ci.yml](../.github/workflows/ci.yml) にあります。
main への push、v*.*.* バージョンタグの push、main 上での手動実行では、先にコードを検査してから次の成果物を作成します。
Pull Request はビルドと検査だけを行い、イメージ、デプロイ添付ファイル、モデルは公開しません。
`models-<content-digest>` のモデル Release 公開時も、そのモデルと現在の main のアプリコミットでデプロイ CI を開始します。

| 配布方式 | ダウンロード先 | 内容とプラットフォーム |
| --- | --- | --- |
| Docker Compose | Actions の `seiyuu-faceid-docker-<commit-sha>` 成果物。末尾はコミット SHA。イメージは Docker Hub | Compose、通常/N150 設定、固定イメージタグ、モデル取得ツール。Linux amd64/arm64 |
| Python ネイティブ | Actions の `seiyuu-faceid-python-<commit-sha>` 成果物。末尾はコミット SHA | Python ソース、uv.lock、設定、systemd テンプレート、モデル取得ツール。CI では Linux amd64 を検査 |
| C++ / Go ネイティブ | Actions の `seiyuu-faceid-native-linux-amd64-<commit-sha>` 成果物。末尾はコミット SHA | Linux amd64 実行ファイル、共有ライブラリー、ライセンス、FTZ と互換 JSON、systemd テンプレート、モデル取得ツール |
| モデル | GitHub Releases の `models-<content-digest>` バージョン。末尾は内容ダイジェスト | ONNX 重み、分類ヘッド、必要なメタデータ。アプリのバージョンから独立 |

3種類のデプロイパッケージには、アーカイブの SHA-256 と内部の SHA256SUMS を付属します。
対応する Actions 実行ページ下部の Artifacts から取得し、まず外側のダウンロードファイルを展開してから、内部の README.md に従います。
デプロイアーカイブの保存期間は14日です。長期保存する場合は自分で取得して保管するか、リポジトリからビルドを再現してください。
成果物の使い方は [GitHub 公式説明](https://docs.github.com/en/actions/tutorials/store-and-share-data) にあります。

デプロイパッケージは約400 MBの ONNX モデルを重複して含めません。
すべてに release/model-source.json を付属し、取得 URL、アーカイブ全体のダイジェスト、許可メンバー、各ファイルのダイジェストとサイズを固定します。
取得ツールは余分なファイル、パストラバーサル、リンク、破損モデル、内容が異なる既存重みの上書きを拒否します。
初回取得には Python 3.11+ の標準ライブラリーを使います。別のマシンで models/ を用意してコピーしても構いません。
これはインストールの準備工程です。C++ / Go サービス実行時に Python は不要です。
オフラインの場合は次を使用します。

~~~bash
python3 tools/fetch_models.py --archive /路径/模型归档.tar.gz
~~~

通常のコードビルドではリポジトリで固定したモデル取得元を使用し、現在は既存 v0.1.0 のモデル専用添付ファイルを使います。
モデル公開によるビルドでは新しく公開した Release を固定します。全ジョブは検証済みの `model-inputs` を共有し、取得元ロックファイルと学習集計を使用します。
同バージョンの過去のデプロイ添付ファイルは取得しません。
すべての方式で同じ FP32 重み、分類ヘッド、認識しきい値を使います。
モデルには付属する上流の利用条件が適用されます。

<a id="检查与发布顺序"></a>

## 検査と公開の順序

1. prepare はアプリコミットとモデル入力を選択します。モデル Release では添付ファイルの許可リスト、GitHub ダイジェスト、SHA256SUMS、内容タグ、安全なメンバー、内外メタデータの一致、分類ラベルと実学習件数を検証して取得元ロックを配布します。
2. quality はロック済み依存関係、Ruff、全 Python テスト、コンパイル、actionlint を検査します。
3. deployments はモデルと学習統計を取得、照合し、Python と Compose のパッケージを生成します。新しいディレクトリへ展開後、Python HTTP サービスを実際に起動し、準備状態、認証、モデル識別子、検出、認識を確認します。2種類の Compose 設定も検証します。
4. native は Ubuntu 22.04 で C++ / Go をビルドし、CTest、通常と native の Go テストを実行します。互換と FTZ のパラメーターを出力し、固定ランダム顔クロップで Python/C++ の特徴量、確率、判定を比較します。パッケージを新しいディレクトリへ展開後、ネイティブ HTTP サービスを起動してエンドポイントを確認します。
5. docker は前提検査の成功後、Python API の Linux amd64/arm64 イメージをビルドして公開します。
6. models はアプリビルドだけで実行します。前述の全ジョブ成功後、モデル専用 Release を生成または検証し、モデルのデプロイ CI を明示的に要求します。モデル起点のビルドはデプロイ成果物の配布で終了し、公開ループを防ぎます。

ランダムクロップの比較は実装の回帰検査に用います。認識精度の評価には該当しません。
実データの精度は [標準データセット精度報告](STANDARD_DATASET_ACCURACY.ja.md) を参照してください。
ネイティブランタイムは glibc を使用し、共有ライブラリーが必要です。
Ubuntu 22.04 ビルドの基準は glibc 2.35 です。ほかのシステムでは動的ライブラリーの互換性を確認します。
既定の native-model.json は Linux x86_64 の FTZ/DAZ を有効にし、native-compatible.json は無効にします。
モデルディレクトリの相対配置と各 JSON の .sha256 ファイルを維持してください。

Docker タグには main の latest、完全なコミットを使う sha- タグ、バージョンタグに対応するセマンティックバージョンがあります。
デプロイパッケージは既定で今回のコミットの sha- タグを参照します。
モデルビルドは Docker の `models-<content-digest>` タグも公開し、Actions 成果物名にモデルタグを付加します。内部アーカイブ名にはアプリコミットを維持し、`BUILD.json` と `release/model-source.json` で正確なモデルアーカイブのダイジェストを固定します。
`latest` を更新するのは通常の main ビルドだけです。モデルは別途取得、検証したディレクトリからマウントします。
既存 Docker イメージは Python API を実行し、ネイティブ FTZ 経路を持ちません。
C++ / Go ネイティブパッケージは既定で API のみを提供します。アップロード用トップページと /docs は Python 方式で利用できます。

<a id="模型-release-的边界"></a>

## モデル Release の範囲

AGENTS.md の公開規約を引き続き適用します。添付ファイルは次のものに限定します。

- seiyuu-faceid-models.tar.gz は models/ 内のモデルと必要なメタデータを含みます。
- SHA256SUMS は上記アーカイブと付随する添付ファイルの検証用です。
- TRAINING_SAMPLES.csv はモデル内の全氏名と実際のフィッティング標本数を示します。
- TRAINING_PROVENANCE.json は分類ヘッドのダイジェスト、固定済み特徴量/分割ファイルのダイジェスト、集計統計を示します。
- MODEL_LICENSES.md はモデルの出所と上流の利用条件を記載します。

アプリコード、デプロイアーカイブ、Compose、API ドキュメント、写真、生の特徴量、評価データはアップロードしません。
Release 説明はモデル取得、対象範囲、全人物と標本数の表を中心に記載します。
リポジトリで固定した取得元の統計は50人、実際にフィッティングした4,064クロップです。
元の学習セット3,574枚と元の検証セット490枚を合算し、テストセット1,051枚は除外します。
統計は現在のローカルモデルが使用した固定分割から出力し、元の公開 CSV、分類ヘッドのラベル順序、ハッシュの対応と照合します。
CI は公開集計統計だけを扱い、学習特徴量を取得しません。

モデルアーカイブはタイムスタンプ、ファイル順序、権限、所有者情報を固定し、アーカイブ SHA-256 の先頭16桁をモデルバージョンに使います。
同じアーカイブは既存の公開を再利用し、アプリコードだけの変更では重みを再アップロードしません。
新規公開は下書き作成から始め、許可リスト内のファイルをアップロードします。
遠隔の各添付ファイルのサイズと GitHub ダイジェストを検証した後で公開します。
失敗時は下書きを残し、再実行で不足ファイルを補えます。
中断したアップロードの0バイト starter プレースホルダーは、下書きかつ許可リスト内の名前の場合だけ削除して再送します。
内容が異なる既存添付ファイルや不完全な公開済みバージョンはエラーとなり、上書きや黙示的な修復は行いません。

<a id="凭据与后续更新"></a>

## 認証情報と今後の更新

tano26/seiyuu-faceid のイメージ公開には、リポジトリに DOCKERHUB_TOKEN Secret が必要です。
モデル公開は Actions 組み込みの GITHUB_TOKEN を使い、models ジョブだけが `contents: write` と `actions: read` を宣言し、公開、明示的トリガー、既存検証実行の検索を行います。
ほかのジョブは読み取り専用です。長期 GitHub キーを別途保存する必要はありません。
パイプラインはサーバーへ SSH 接続せず、実行中サービスの自動置換もしません。

アプリ更新後は main に push します。
重みを更新する前にローカルで実際の学習元を確認し、公開用集計を出力します。

~~~bash
uv run python tools/export_training_metadata.py --output /tmp/training-new.json
~~~

このコマンドは現在の固定データと分類ヘッドを読み、集計だけを出力します。
重複や交差のある分割、クラス不一致、不正な総数を拒否します。
新しい統計を確認後、release/training.json を更新します。
準備済みの新しいモデル専用アーカイブを CI に渡し、release/model-source.json の固定 GitHub ダウンロード URL、アーカイブと各メンバーのダイジェスト、サイズを更新します。
元モデルのアーカイブは事前にダウンロード可能である必要があります。
CI は開発用コンピューターの無視対象ディレクトリにアクセスせず、モデルの再学習もしません。
初回の準備や出所変更では、まずモデル専用のソースバージョンを手動公開し、その後パイプラインで検証済みの内容バージョンを生成できます。

### モデル公開のトリガー

手動公開は `models-<content-digest>` タグの `release.published` で検知します。公開前に5つの検証済み添付ファイルをすべて用意します。
CI 公開は `tools/publish_models.py --dispatch` を使い、タイプ `model-published` と `client_payload.tag` を持つ `repository_dispatch` を送信します。GitHub は GITHUB_TOKEN が生成する通常のワークフローイベントを抑制しますが、明示的な dispatch では起動できます。[GitHub の公式規則](https://docs.github.com/en/actions/concepts/security/github_token)を参照してください。
公開ツールは直近100件の CI 実行を調べ、このリポジトリの信頼できるモデルイベントで実行中または成功済みの `Model <tag>` だけを再利用し、PR と fork の実行は除外します。失敗した実行や未送信のトリガーは、Release 公開後も公開ツールの再実行で再試行できます。
モデルイベントのビルドは選択した Release を分離して検証し、不正な場合は終了します。同じ実行の全デプロイパッケージが選択したモデルを使います。その後の通常コードビルドではリポジトリの固定取得元を既定として使い、既定モデルを変えるには取得元を明示的に更新します。

既存モデル Release のデプロイ成果物を作る場合や失敗した実行を再試行する場合は、main の **Run workflow** で `model_tag` を指定します。次の例のタグを置き換えて CLI から実行することもできます。

~~~bash
gh workflow run ci.yml --ref main -f model_tag=models-0123456789abcdef
~~~

ワークフローとスクリプトを先に main に反映します。手動公開では、モデルタグの参照先コミットにも `release.published` のリスナーが必要です。GitHub はタグのコミットからそのイベントのワークフローを読み込みます。リスナー追加前の既存タグは、上記の `model_tag` コマンドか main への明示的な repository dispatch を使います。[GitHub のワークフロートリガー規則](https://docs.github.com/en/actions/concepts/workflows-and-actions/workflows)を参照してください。
実行名は `Model <tag>` です。モデル公開の成功とデプロイ CI の成功は別の状態なので、配備前に対応する実行を確認してください。

設定段階でローカル検証を完了します。その後のコミット、push、クラウド処理確認はユーザーの承認範囲で実施します。
クラウド全体のビルド、Docker Hub push、Release アップロードの結果は、対応するコミットの Actions 実行記録を基準とします。
